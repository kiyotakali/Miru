CareEngine 唤起机制图解

Per-user 后台线程在「等待 → 醒来 → 评估 → 接着等」无限循环。任何人可以打断它的等待，但不能让它跳过 4 层硬地板。

🌙 _loop 主循环
self._wake.wait(timeout=wait_secs) → 醒来后必跑 _tick() → 回到 wait
每个用户独立线程，各等各的，互不影响

评估 + 决策（单次 LLM 调用）

_evaluate(snapshot, catchup)
输入：完整 snapshot（today_chat / human / persona / identity / 情绪曲线 / 信号 buffer / 活跃 DDL / 日记片段）
输出 JSON：{ speak, wait_minutes, message, thought }
📨 speak: true
→ _deliver(message)
写 chat_history
+ SSE 推送
+ Web Push
+ 记 last_send_time
⏳ wait_minutes: 1-30
_next_wake_at = now + N×60
N 分钟后再来评估
🤐 wait_minutes: 0
_next_wake_at = 0
不主动调度，等用户来
📐 它们怎么不冲突？
  1. signal 永远不能直接发消息——只能让 _loop 醒一次跑 _tick；4 层硬地板不过就回去继续等
  2. _next_wake_at 只有两个写入者：chat_out（设 5min cooloff）和 LLM 决策（设 wait_minutes 或 0）。后写覆盖前写。chat_out 优先级最高（"刚结束的对话比之前的等待更重要"）
  3. HEARTBEAT 30min 是死锁预防——只有当 _next_wake_at == 0 时才生效
  4. 所有 signal 都进 buffer 不丢失，IN/POST 期间硬地板挡住评估，但信号继续累积；POST 结束时一次性 catchup 评估
  5. 每个用户独立 1 个线程 + 1 个 _wake event + 1 个 buffer，多用户互不影响

真实场景演练

场景 1：用户聊天中收到新截屏（不冲突）

14:00:00
signal 用户发"你好" → chat_in + 切 IN _wake.set，state=IN_CONVERSATION
14:00:00.05
gate A _tick 醒来 → 硬地板 A：state=IN → return 不评估，但 signal 入 buffer
14:00:10
signal 截屏分析完 → screenshot _wake.set，再次入 buffer
14:00:10.01
gate A _tick → 仍然 IN → return 截屏数据还在 buffer
14:00:30
signal Miru 回复送出 → chat_out + 切 POST _next_wake_at = now+5min
14:05:30
eval 5min cooloff 到期 → 4 层都过 → catchup 评估 LLM 看到完整对话+期间截屏，决定要不要追加一句

场景 2：LLM 设 wait_minutes=10，5 分钟后被 chat_in 打断

10:00:00
eval LLM 决策 wait_minutes=10 _next_wake_at = 10:10:00
10:05:00
signal 用户发消息 → chat_in _wake.set 提前打断（原本要等到 10:10）
10:05:00.01
gate A 硬地板 A：state=IN → return 原来的 _next_wake_at=10:10 还在但已无意义
10:05:30
signal chat_out → POST → _next_wake_at = 10:10:30 covered 10:10:00（5min cooloff 比 LLM 之前的 10min 更短，但 chat_out 总是覆盖）
10:10:30
eval POST 5min 到期 → catchup 评估

场景 3：HEARTBEAT 兜底（用户半天没动）

10:00
eval LLM 决策 wait_minutes=null → _next_wake_at 不变（保持 0） "我没意见，让系统兜底"
10:00 算 wait_secs
_next_wake_at(0) > now? 不 → wait_secs = HEARTBEAT_INTERVAL = 1800
10:30
eval 30min 自然 timeout → 4 层硬地板 → 评估 兜底循环

场景 4：LLM 输出 wait_minutes=0（"等用户主动"）

15:00
eval LLM 觉得"这事不该我管，等用户" → wait_minutes=0 _next_wake_at = 0
15:00 算 wait_secs
_next_wake_at(0) > now? 不 → wait_secs = 1800（依然走 HEARTBEAT） 这是故意的安全网——防止"等用户主动"持续不被叫醒
15:30
eval HEARTBEAT 醒来 → 评估 如果 LLM 还输出 0，每 30min 一次评估，不烦不丢

常见误解

Q：signal 来了会不会打断正在跑的 LLM 评估？
A：不会。_tick 是同步执行的（包括 LLM 调用）。signal 在 _tick 期间来只是 _wake.set()，等 _tick 结束 _loop 回到 wait 时立刻看到 _wake 已 set，再跑一次 _tick。但下一次会被 EVAL_THROTTLE 60s 挡掉。
Q：用户刷屏发 10 条消息会不会让 CareEngine 评估 10 次？
A：不会。第一条 chat_in 切 IN_CONVERSATION，之后所有 signal 都被硬地板 A 挡住——signal 进 buffer 但不评估。chat_out 后 5min cooloff 才会做1 次 catchup 评估，看到这 10 条全部消息。
Q：HEARTBEAT 和 wait_minutes 会不会同时触发？
A：不会。它们是 wait_secs 计算的二选一：if _next_wake_at > now: wait_secs = _next_wake_at - now; else: wait_secs = 1800。HEARTBEAT 只在 _next_wake_at == 0 或已过期时才生效。
Q：Miru 之前发过的话和 thought，下次评估时还能看到吗？
A：部分能看到。
  • 📤 message 通过 chat_history.json 看到（修复后通过 today_chat 字段，包含当日所有"Miru主动: ..."）
  • 💭 thought 只看到最近一次（_last_thought 是内存字段不持久化），重启会丢
  • ⚠️ 这是新发现的 bug：应该让 LLM 看到自己今日所有 thought 轨迹，而不是只一条。修复方案：从 care_log.json 拉今日记录加进 snapshot
